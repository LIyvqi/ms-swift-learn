本页严格区分三类数字：确定性检索基础设施、金标签专家协议上界、真实模型逐轮生成。前两类不能冒充训练后模型效果。

## 确定性测试

单元测试覆盖三种后端和最大层级、先定位后检索约束、直接结束、多标签 Case 的类别—路由投影、验证/测试泄漏、候选 Case 隔离、专家闭环和逐状态监督对齐。当前测试结果为 8/8 通过。

最终按底层 `record_id` 去重后的 200 条离线检索结果：

| 指标 | 结果 |
|---|---:|
| Locate Recall@6 | 95.17% |
| Top-1 子树支持召回 | 26.75% |
| Top-3 子树支持召回 | 63.50% |
| 全 Case 库 Recall@6 | 87.83% |
| Top-1 候选记录占比 | 8.95% |
| Top-3 候选记录占比 | 24.22% |
| Locate 平均延迟 | 131.8 ms |
| Top-3 搜索平均延迟 | 44.4 ms |

Locate@6 较高，但 Top-3 支持召回只有 63.5%，说明目录路由仍是当前明确瓶颈。后续应比较硬关系图扩展或真实语义向量，而不是扩大提示词。`evaluate_pipeline.py` 中专家完成率、决策准确率和类别 F1 都为 100%，但这是由金标签生成动作的协议上界，只能证明环境闭环，不是训练后模型能力。

## SFT 冒烟训练

2026-08-31 使用 Qwen3.5-0.8B-Base、LoRA rank 32 和 24 条冒烟数据执行 3 step：

| 项目 | 结果 |
|---|---:|
| 可训练参数 | 21.6453M（2.4748%） |
| 训练 loss | 1.0507 |
| 验证 loss | 0.8819 |
| 验证 token accuracy | 85.78% |
| 总训练时间 | 86.8 秒 |
| 框架峰值显存 | 170.5 GiB |

物理 batch 8 在第一个 5k-token 长样本上达到约 182 GiB 已分配显存，随后申请 19.72 GiB 时 OOM。物理 batch 4 可完成 24 条冒烟集，但全量随机批次第 6 步达到 190.99 GiB；batch 3 在第 85 步又达到 191.19 GiB。两者都只剩约 0.5～0.7 GiB，不能作为 191.7 GiB 卡的可靠长跑配置。正式默认最终固定为物理 batch 2、梯度累积 4，有效 batch 8，并每 50 步保存以防中断。

这轮只有 3 step，作用是验证数据、模板、显式思考监督、反向传播、验证和保存链路；不能据此声称 Agent 已学会完整多轮工具策略。

## 真实逐轮生成与 GRPO 冒烟

同一个 `checkpoint-3` 在 24 条样本上的温度 0 逐轮生成结果为：完成率 0、无效动作率 100%、平均 5 轮。典型错误包括把协议字段 `tool` 写成 `action`、一轮输出多个动作、产生未闭合 JSON，以及生成不在合法类别表中的临时类别。这说明 3-step 只验证了反向传播链路，尚未学会 Agent 协议。

随后使用该检查点执行 1-step GYM-GRPO，真实完成了 vLLM 多轮 rollout、四个自定义奖励、环境奖励、反向传播和保存：

| 项目 | 结果 |
|---|---:|
| 平均轮数 | 5.0 |
| 平均 completion token | 990.6 |
| 总 reward | -1.25 |
| reward 标准差 | 0.0 |
| KL | 0.000681 |
| 单步时间 | 71.3 秒 |
| 框架峰值显存 | 122.75 GiB |

所有采样都因协议错误得到相同惩罚，因此组内 advantage 为零，不能形成有效 GRPO 学习信号。课程保留这个负结果，用来强调“先通过 SFT 学会动作语法，再用 RL 优化策略”的必要性。更长 SFT 和后续真实评测会单独追加，不能用本次 1-step GRPO 宣称效果提升。

## 正式两阶段 SFT

完整 1600 条轨迹训练 1 epoch，共 200 step：

| 项目 | 结果 |
|---|---:|
| 训练时间 | 25 分 57 秒 |
| 训练 loss | 0.1099 |
| 验证 loss | 0.03514 |
| 验证 token accuracy | 98.79% |
| 外部采样物理显存峰值 | 183.77 GiB |
| 外部采样平均 GPU 利用率 | 89.29% |

真实 24 条逐轮生成不再产生非法 JSON，但全部连续执行 5 次 `locate`，完成率仍为 0。这说明普通多轮 SFT 的 teacher-forcing 指标不能替代真实状态推进评测。原因是思考模型在普通多轮训练中保留历史 `<think>` 并监督所有 assistant，真实推理却移除历史思考；0.8B 模型只稳定学会了首轮动作。

第一版逐状态修复错误地把 433 条直接结束样本也重复放入第二阶段。完成率变成 100%，但 24 条全部直接 `finish`，安全准确率和类别 F1 都只有 20.83%。这次负结果表明，阶段二不能重新改变首轮动作先验。

最终版本只保留 1167 条“已经收到环境观察”的检索轨迹，目标为 `search 574 / finish 445 / 二次 locate 148`，从正式轨迹 SFT 检查点重新训练 146 step：

| 项目 | 结果 |
|---|---:|
| 训练时间 | 11 分 22 秒 |
| 验证 loss | 0.01931 |
| 验证 token accuracy | 99.34% |
| 24 条完成率 / 无效动作率 | 100% / 0% |
| 24 条完整检索链 | 7 / 24 |
| 24 条安全准确率 / 类别 F1 | 41.67% / 33.33% |

最终策略已经真实形成 17 条直接结束和 7 条 `locate → search → finish`，所以两阶段 SFT 解决的是“能否推进 Agent 状态”，不是把 0.8B 模型包装成高质量审核器。

## 有效 GRPO 信号与隔离测试

从最终状态 SFT 执行 3-step GRPO 后，reward 标准差为 0.823 和 0.476，不再是早期实验的全零 advantage；四个自定义奖励和 GYM 环境奖励都出现非零差异。3 step 在 24 条 smoke 上略有退化，因此又独立执行了 10 step：耗时 3 分 35 秒，采样 reward 从 1.156 上升到中段最高 2.180，所有记录都保留在原始日志中。

固定 24 条训练 smoke 上，10-step GRPO 把安全准确率从 41.67% 提到 54.17%，类别 F1 从 33.33% 提到 36.11%，完整检索链从 7 条增至 12 条。但 smoke 被 RL 使用过，不能据此声称泛化提升。

最终在完全隔离、从未进入 Case 库和训练的 200 条 test 上对比：

| 指标 | 状态 SFT | 10-step GRPO | 变化 |
|---|---:|---:|---:|
| 完成率 | 99.00% | 98.50% | -0.50 pp |
| 无效动作率 | 0.80% | 1.15% | +0.35 pp |
| 安全准确率 | 49.00% | 52.00% | +3.00 pp |
| 类别 F1 | 43.67% | 41.50% | -2.17 pp |
| 平均 locate / search | 0.26 / 0.26 | 0.38 / 0.375 | 检索增加 |
| 记忆类别召回 | 10.92% | 14.50% | +3.58 pp |
| 置信质量代理分 | 0.5801 | 0.6032 | +0.0231 |

结论是混合的：10-step GRPO 增加检索并提高二分类安全准确率和置信代理分，但多标签 F1、完成率和协议稳定性小幅下降。当前证据只支持“RL 链路和学习信号有效”，不支持“整体审核效果已经稳定提升”。下一轮应优先增加独立测试和按类 reward 诊断，而不是继续在 24 条 smoke 上调参。

GRPO 日志中的 `memory(GiB)=246.1` 大于本机约 191.7 GiB 物理显存，显然不是可直接解释为物理驻留峰值的指标；实际训练正常完成且无 OOM。容量规划必须使用 ROCm/NVIDIA 的外部物理显存采样，不能拿该框架字段估算设备需求。

## 已确认的工程经验

1. 多标签 Case 必须按每个类别建立检索投影，否则“第一个标签 + 第一个路由”会生成语义错误的目录。
2. 返回结果应按底层事实 `record_id` 去重，否则同一 Case 的多个投影会挤占 Top-K。
3. `locate` 既不能只返回宽泛父节点，也不能只靠最深目录摘要；parent-child 子记录支持信号能在候选规模和召回之间取得更合理的平衡。
4. 最大 token 长度而非均值决定批量显存上界。该卡上物理 batch 4 已接近实用容量上限。
5. Experience Wiki 适合记录“如何使用库”和失败模式，但业务真值仍必须留在正式规则、Case 和知识库中。

## 组织方式消融

针对“Wiki、图谱、GraphRAG 是否应该直接成为主组织方式”的问题，本课先实现了无需 LLM 抽图的类别硬图基线。固定 200 条测试中，当前分层 Top-3 支持召回为 62.75%；自由图扩展降到 49.50%，候选占比从 22.54% 增至 37.91%；限制每个库一个路径的共识图进一步降至 40.33%。

因此当前不把图路由并入 Agent。推荐把 Wiki 用于人工规则编辑，把关系图当可重建索引，并等待真实人工关系和 Case 后再做消融。完整架构与维护流程见 [组织方式研究](MEMORY_ORGANIZATION_RESEARCH.md)。
