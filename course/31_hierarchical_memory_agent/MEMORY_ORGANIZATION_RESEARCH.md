# 规则、Case 与知识的组织方式研究

## 1. 先给结论

本场景不应直接照搬“纯 Wiki”“纯知识图谱”或“全量 GraphRAG”。更合适的是一个自定义的 **Human-Governed Memory Fabric（人工治理记忆层）**：

```text
                    人工治理真值层
       ┌──────────────┼──────────────┐
       │              │              │
   规则 Wiki       Case Ledger      知识库/CMS
  少量、强结构       大量、强审计      长文、分层目录
       │              │              │
       └──────────────┼──────────────┘
                      ↓
             可重建的关系与索引层
    显式链接 + Backlink + BM25 + Vector + Schema Graph
                      ↓
              Agent 检索与训练层
       locate / search / follow / read / finish
```

关键原则是：

- 人工编辑的原始规则和人工确认 Case 才是真值；
- 图、向量、社区摘要和 Wiki backlink 都是可删除重建的索引；
- 模型可以提出链接、规则冲突和候选 Case，但不能自动成为正式事实；
- 不强迫三个库迁移到同一种物理存储，只统一身份、关系和访问协议。

这个方案吸收 Wiki、知识图谱和 GraphRAG 的有用部分，但不以任何一个热点名称定义系统。

## 2. 为什么不直接选一种现成形态

本文把“GraphWiki”理解为“人可读页面 + 显式链接/关系图”的产品形态，不绑定某个同名仓库或协议；真正需要比较的是页面真值、关系索引和检索行为，而不是名称。

| 方案 | 人工阅读/修改 | 大量 Case | 跨库多跳 | 真值审计 | 本场景判断 |
|---|---:|---:|---:|---:|---|
| 纯目录/数据库 | 中 | 强 | 弱 | 强 | 适合底层存储，不够支持关系检索 |
| 纯 Wiki | 强 | 弱到中 | 依赖人工链接 | Git 方式很强 | 适合规则，不适合把海量敏感 Case 全变成页面 |
| 纯图数据库 | 弱到中 | 强 | 强 | 需要额外治理 | 适合派生索引，不宜当人工唯一入口 |
| 全量 GraphRAG | 生成摘要可读 | 中 | 强 | LLM 派生内容不是事实 | 适合分析，不宜直接决定逐条审核 |
| 当前分层联邦库 | 中 | 强 | 中 | 强 | 简单可靠，但跨库关系较弱 |
| 人工治理记忆层 | 强 | 强 | 强 | 强 | 推荐，复杂度可按需开启 |

### 2.1 Wiki 的价值与边界

Wiki 最有价值的不是页面外观，而是稳定页面身份、双向链接、章节级阅读、历史版本和人类可维护性。2026 年的 [LLM-Wiki](https://arxiv.org/abs/2605.25480) 把检索从一次 Top-K lookup 改成 `search → read → follow links → 判断证据是否足够`，与本课 Agent 的多轮导航方向一致。

但 Case 量大、可能含隐私或有害原文，把每条真实 Case 直接存进 Git Markdown 会带来权限、删除、脱敏和仓库膨胀问题。因此建议“规则是真正可编辑 Wiki；Case 是带审核工作流的 Ledger/数据库；Wiki 只提供按需渲染的 Case 视图和反向链接”。

### 2.2 显式图谱的价值与边界

图最适合表达目录树无法自然表达的关系，例如：

```text
规则 R12 --HAS_EXCEPTION--> 例外 E4
规则 R12 --REGRESSED_BY--> 人工 Case C91
Case C91 --ALSO_MATCHES--> 规则 R18
知识 K7  --EXPLAINS--> 概念 X
概念 X   --ALIAS_OF--> 概念 Y
```

如果让 LLM 从全部正文自由抽三元组并直接当真值，错误实体合并、关系幻觉和缺失例外会变成新的治理负担。推荐只把人工链接和确定性 schema 边当作“硬边”；模型发现的关系先进入 `suggested` 候选区，人工确认后才能用于高风险决策。

### 2.3 GraphRAG 的价值与边界

[Microsoft GraphRAG](https://microsoft.github.io/graphrag/) 会从文档抽取实体、关系和 claim，用 Leiden 构建层级社区并生成 community report；它提供 Global、Local、DRIFT 和普通向量检索。Global/community report 很适合回答“当前政策主要有哪些主题”“哪些规则簇冲突或覆盖不足”等全局分析问题；Local/DRIFT 更接近逐条案例检索。

逐条审核通常需要精确条件、例外和原文证据，生成式社区摘要可能压缩掉关键边界，而且完整索引会消耗较多 LLM 资源。因此本课程不把 GraphRAG 放在在线主链路，而把它作为可选的离线分析器：发现主题、覆盖缺口和候选关系；最终在线 Agent 仍读取原始规则修订和人工 Case。

### 2.4 其他值得借鉴的部件

- [HippoRAG 2](https://github.com/OSU-NLP-Group/HippoRAG) 使用图上的关联激活/PPR 支持跨文档联想，适合做“从命中概念扩展到相关规则和 Case”的实验基线；
- [Graphiti](https://github.com/getzep/graphiti) 强调 episode 来源、事实关系和可追溯更新。用户当前不需要复杂过期规则，所以不必引入完整时态图，但“所有派生关系能回到原始 episode/source”非常值得保留；
- [WikiSkill](https://arxiv.org/abs/2608.27454) 分开原始经验、持久知识和执行产物。本课只借鉴这种分层，把 Experience Wiki 用于训练工程经验，不创建 Skill，也不让经验页覆盖业务规则。

## 3. 推荐的数据平面

### 3.1 规则：可编辑 Wiki 页面

规则数量相对少、变更需要 review，适合一规则一页 Markdown + 结构化头部：

```yaml
id: rule:R-FRAUD
revision: 7
status: active
scope: 通用平台
category: financial_crime
priority: 90
owner: safety-policy
reviewers: [alice, bob]
```

正文按固定章节组织：定义、成立条件、例外、处置、测试 Case、变更理由。页面可以使用稳定链接 `[[case:C-0091]]`、`[[knowledge:money-mule]]`；编译器负责检查悬空链接、重复 active 规则和非法类别。

### 3.2 Case：审核台账而非纯 Wiki

Case 使用数据库或对象存储保存原文，元数据至少包括：

```json
{
  "case_id": "case:C-0091",
  "decision": "UNSAFE",
  "categories": ["financial_crime"],
  "matched_rule_revisions": ["rule:R-FRAUD@7"],
  "evidence_spans": [{"field": "response", "start": 18, "end": 43}],
  "review_status": "approved",
  "reviewed_by": "reviewer_7",
  "reviewed_at": "2026-09-01",
  "source_uri": "case-ledger://C-0091"
}
```

人工页面显示 Case、相似规则、相邻 Case 和影响范围，但保存动作写回 Ledger。`candidate`、`approved`、`rejected` 必须是分离状态；只有 approved 能进入生产检索和下一轮训练。

### 3.3 知识：保留原 CMS/目录

知识可能来自独立 Wiki、文档站或数据库，无需搬到规则仓库。每份文档只需稳定 `knowledge_id`、章节锚点、来源、权限和修订号。长文分块只是索引行为，引用仍回到“文档 ID + 修订 + 章节”，不能只返回匿名 chunk。

### 3.4 关系注册表：轻量硬图

跨库关系单独保存，不复制节点正文：

```json
{"edge_id":"edge:E-102","from":"rule:R-FRAUD@7","type":"REGRESSED_BY","to":"case:C-0091","origin":"human","status":"active","reason":"该 Case 覆盖例外边界"}
```

推荐关系分级：

| 级别 | 来源 | 是否可直接用于在线依据 |
|---|---|---:|
| 硬边 | 人工确认或确定性 schema | 是 |
| 监督边 | 已标注训练数据推导 | 可以，但要显示来源 |
| 软边 | embedding、LLM 抽取或共现 | 只用于召回，不作为结论依据 |
| 候选边 | Agent/模型新发现 | 否，等待人工确认 |

图数据库不是必需条件。中小规模可先用 JSONL/SQLite + 邻接表；只有图遍历、并发和规模证明需要时再换 Neo4j、FalkorDB 或其他后端。

## 4. 推荐的检索流程

```text
Query / Case
    ↓
1. 来源与目录定位：BM25 + Vector + 元数据过滤
    ↓
2. 命中稳定实体：规则、Case、知识章节
    ↓
3. 受控图扩展：只沿允许关系走 1～2 hop
    ↓
4. Rerank：正文相关性 + 边可信度 + 修订状态
    ↓
5. Read：读取原始规则章节和人工 Case，而不是只读摘要
    ↓
6. Agent 决策：结论 + 原文证据 + 规则修订 + Case ID
```

第一阶段不要直接上自由图遍历。先做四组可复现实验：

1. 当前 Hybrid Flat；
2. 当前 Hierarchical Locate；
3. Hierarchical + 人工/确定性硬边扩展；
4. 可选 GraphRAG/LLM 图扩展。

只有第 3 或第 4 组在 `Recall@K`、最终 F1、引用正确率或人工维护成本上取得稳定增益，才把相应复杂度加入主链路。

### 4.1 当前确定性消融结果

本课已经在固定 200 条测试集上实现了两种不使用测试金标签的硬关系图路由：自由类别 hub 扩展，以及每个独立库最多选一个路径的跨来源共识。结果如下：

| 路由 | Top-3 支持召回 | 候选记录占比 | 平均延迟 |
|---|---:|---:|---:|
| 当前分层路由 | **62.75%** | 22.54% | 158.5 ms |
| 自由硬图扩展 | 49.50% | 37.91% | 170.6 ms |
| 受控跨库共识图 | 40.33% | **18.61%** | **146.5 ms** |

本表为了公平让三种方法都直接返回 3 条路径；前文基础设施评测先请求 6 条再取前三条，因此当前分层路由显示为 63.50%，两种口径不能混作随机波动。

自由图扩展被高频 Case 类别支配，召回下降且候选膨胀；受控共识虽然更快、更窄，但错误共识会把三个库一起带到错误类别。当前证据不支持把这两种图路由接入主链路，代码保留在 `evaluate_organization_options.py` 作为负结果和后续基线。

这不证明“所有图检索都无效”，只证明简单类别 hub 不适合当前数据。下一步若继续研究，应优先增加真实人工关系、例外边和更好的语义 seed，再与当前 62.75% 基线比较；不能仅调权重直到测试集数字好看。

## 5. 人工修改就是“自进化”

这里的进化不等于模型随意改库，而是一条治理流水线：

```text
人工编辑规则 / 审批 Case
        ↓
Schema、链接、权限和冲突检查
        ↓
图谱影响分析：会影响哪些规则、Case、数据和指标
        ↓
回归集：旧 Case + 新 Case + 相邻类别 hard negative
        ↓
人工批准合并
        ↓
增量重建 BM25 / Vector / 邻接表
        ↓
生成下一轮 SFT/GRPO 数据，但不自动启动生产发布
```

建议规则修改必须自动产生：

- 本次 revision 与上一 revision 的结构化 diff；
- 新增/删除的条件、例外和处置；
- 直接关联和一跳相邻的回归 Case；
- 旧模型在受影响 Case 上的退化报告；
- 索引构建摘要和可回滚修订号。

人工 Case 审批必须完成：去重、证据 span、匹配规则修订、审核人和来源。模型只负责推荐相似项与候选链接。

课程提供了一个不依赖图数据库的影响分析原型：

```bash
python course/31_hierarchical_memory_agent/analyze_change_impact.py \
  --rule-id BT-001
```

它沿确定性的“规则—类别—知识—Case—相邻规则”关系生成回归范围，只输出稳定 ID 和统计，不复制 Case 原文。这个功能先解决人工改规则时最实际的问题，再决定是否需要专业图后端。

以 `BT-001` 为例，当前脚本实际找到 19 条直接正例、715 条相邻类别 hard negative、714 条 SAFE 对照和 2 篇关联知识文档；还给出了 4 个多标签共现类别与 3 条同路由相邻规则。这里的数量来自已标注训练库的确定性关系，不是模型生成的“看起来相关”。它说明轻量关系注册表已经能完成变更回归选集，尚无证据表明必须先部署完整图数据库。

## 6. 与训练 Agent 的关系

外部记忆不是替代训练，而是把能力拆成两部分：

- 参数内学习稳定行为：动作协议、何时检索、如何比较条件/例外、如何引用；
- 参数外维护快速变化事实：具体规则修订、人工 Case 和知识内容。

新规则或新 Case 加入后，先通过索引即时生效；积累到足够数量再生成训练轨迹，让 Agent 学会更好的导航策略。这样避免每次规则文字修改都重训，也避免模型参数成为无法人工检查的唯一规则载体。

## 7. 实验与验收指标

### 检索

- Rule Recall@5/10；
- Approved Case Recall@5/10；
- 多跳 Path Recall；
- 命中原始修订的比例；
- 平均检索 token、延迟和候选子树占比。

### 决策

- 每类 recall、micro/macro F1；
- 过杀、漏放与多标签遗漏；
- 引用规则修订正确率；
- evidence span 精确率；
- 高置信自动处置覆盖率和覆盖内错误率。

### 人工治理

- 修改一条规则所需时间；
- 自动找出的受影响 Case 覆盖率；
- 悬空链接、冲突规则和重复 Case 数；
- 候选 Case 到 approved 的人工通过率；
- 索引重建时间和可回滚性。

## 8. 实施顺序

1. 保留当前三个独立库和统一 ID；
2. 先把规则改成带结构头部的可编辑页面，Case 保持 Ledger；
3. 增加显式关系注册表和 backlink/影响分析，不安装图数据库；当前简单类别图消融已失败，因此不接入在线主链路；
4. 有足够人工关系后，再比较“无图、人工硬图一跳、PPR/GraphRAG”三组召回与端到端效果；
5. 硬图确有增益后再选图后端；
6. 最后才考虑 LLM 自动抽关系和社区摘要，并始终放在候选/分析层。

这条路线把最有价值的人工可维护性先落地，同时给图检索留出实验空间，不会一开始就背上复杂基础设施。
