# 显式 CoT-GRPO：5-step 真实训练记录

本记录只报告本机实际运行得到的数据。实验最初计划训练 100 step；跑完前 5 step 后，按学习者要求停止，因为当时估算完整训练需要约 2 小时。由于原任务只在第 100 步保存，停止后又用同一配置正式运行 5 step 并保存 `checkpoint-5`。

## 实验配置

| 项目 | 实际值 |
|---|---|
| 学生起点 | 339-step 全参混合 SFT 检查点 |
| 数据 | 900 条 GSM8K Prompt-only 训练集 |
| 训练方法 | ms-swift 官方 v4.4.3 标签源码，GRPO + LoRA |
| LoRA | rank 16，alpha 32 |
| 每组候选数 | 8 |
| 每设备 batch | 8，即每步一个完整 GRPO 组 |
| 训练步数 | 5 |
| 总有效 rollout | 40 |
| 生成上限 | 2048 token |
| 学习率 | `5e-6`，默认调度器在第 5 步衰减到 0 |
| KL 系数 | 0.001 |
| vLLM 模式 | colocate，规划比例 0.60 |
| 奖励 | 答案、严格结构、可执行计算、数值覆盖、过程答案一致性 |

版本口径以 [训练环境笔记](../../TRAINING_ENVIRONMENT.md) 中保存的官方标签提交 `e1287928be4451b9ed5e2fb00a24ad3c8f61287b` 为准。该标签的上游源码没有把运行时版本字符串改成正式版，因此 `swift.__version__` 和安装元数据会显示 `4.5.0.dev0`；这不是本课程自行修改的版本号。

运行命令：

```bash
cd /mnt/workspace/ms-swift-learn

STEPS=5 RL_BATCH=8 NUM_GENERATIONS=8 \
  MAX_COMPLETION_LENGTH=2048 VLLM_MEMORY=0.60 \
```

## 训练侧观察

| 指标 | 第 1 步 | 第 5 步 | 5 步均值 |
|---|---:|---:|---:|

| 答案正确奖励 | 0.000 | 0.125 | 0.050 |
| 严格结构奖励 | 0.125 | 0.250 | 0.175 |
| 可执行计算奖励 | 0.281 | 0.562 | 0.425 |
| 题目数值覆盖 | 0.562 | 0.875 | 0.725 |
| 过程答案一致性 | 0.000 | 0.250 | 0.150 |
| completion 平均长度 | 1184 token | 658 token | 845 token |
| 到达 2048 上限的比例 | 50.0% | 25.0% | 32.5% |
| 每步耗时 | 75.2 秒 | 62.9 秒 | 65.6 秒 |

`completions.jsonl` 在保存检查点时把最后一步完全相同地记录了两次。`inspect_rollouts.py` 默认去除这种重复，因此总数按 5×8=40 个有效 rollout 计算，而不是文件表面的 48 个。

训练曲线说明过程奖励很快提供了方向：输出变短，计算和题目数值覆盖提高。但是前三步的 8 个候选全部答错，答案奖励在组内没有差异；这些步主要依靠过程代理奖励学习。代理指标上升不能代替答案正确率。

## 显存结论

本机物理 HBM 总量由 `torch` 和 `rocm-smi` 共同确认为 191.69 GiB。正式 5-step 训练每秒用 `rocm-smi` 独立采样，得到：

| 显存口径 | 数值 |
|---|---:|
| 物理 HBM 总量 | 191.69 GiB |
| `rocm-smi` 实际峰值 | 188.10 GiB |
| 峰值时剩余空间 | 约 3.59 GiB |
| 实际占用比例 | 约 98.1% |
| ms-swift 本次 `memory(GiB)` 最大值 | 185.74 GiB |
| 早期 batch 16 冒烟日志字段 | 245.5 GiB |

245.5 GiB 大于设备物理总量，所以它不可能是某一时刻的真实 HBM 占用。它属于框架内部的统计口径，不能拿来判断设备是否支持；容量判断应以 `rocm-smi`、设备总量和是否 OOM 为准。

本机确实能跑 batch 8，但 3.59 GiB 余量很小，属于偏激进配置。若同一 GPU 上还有其他进程，或换成长 Prompt、更大模型、更长生成，都可能 OOM。迁移到显存更小的设备时，先同时降低 `RL_BATCH` 和 `NUM_GENERATIONS`，保证 batch 能整除候选数，例如：

```bash
SMOKE=1 RL_BATCH=4 NUM_GENERATIONS=4 \
  VLLM_MEMORY=0.45 MAX_COMPLETION_LENGTH=1024 \
  bash course/03_grpo/train_cot_rules.sh
```

1024 token 只适合先验证容量；本机早期测试的截断率较高，正式质量实验仍应尽量恢复 2048，并重新测峰值。

## 训练经验

1. 5 step 是链路测试，不是能力实验。这里只看了 5 个训练 Prompt、40 个 rollout，样本覆盖远远不够。
2. 短跑会改变学习率语义。设置 `STEPS=5` 后，默认调度器会在第 5 步降到 0；它并不等价于 100-step 任务的前 5 步。严谨比较不同步数时应固定调度策略或比较相同学习率轨迹。
3. 训练 reward 必须配独立验证。总奖励从 0.25 升到 0.625，但验证正确率不变，说明模型先学到了更容易的过程代理特征。
4. 稀疏答案奖励对弱模型很困难。前三组没有一个正确候选，答案项无法产生组内相对信号；更强的 SFT 起点、课程化题目或部分分奖励会更有效。
5. 长度上限不是越大越好。2048 减少了“答案被截掉”，但也允许 0.8B 模型长时间重复。应同时使用收束奖励、抽查文本和截断率，而不是继续无限增加上限。
6. 单步 batch 8 已接近本机显存上限。提高显存利用率能加快吞吐，但 98.1% 峰值缺少故障余量；长期实验更适合略降 batch，或确保 GPU 独占。
7. 下一轮建议先跑 20～30 step，在第 5、10、20、30 步分别保存并评测。只有验证正确率、格式率和长度同时改善，才值得继续到 100 step。
